# Technical Decisions

Lightweight records for decisions that affect future implementation. Product requirements remain in `PROJECT_SPECIFICATION.md` and the original PDF.

Keep the masthead off-white with the existing neutral border token so the yellow sparkle remains visible. Keep the centralized palette and typography unchanged. ## TD-01 — Client-side document pipeline

**Context:** Lyrics are private user input; the product is a static utility (source PDF pp. 2, 5, 7). **Decision:** React and TypeScript run normalization, PDF creation and preview in the browser. One generated byte snapshot feeds later preview and download. No backend, persistence, authentication, remote lyric provider, telemetry or state library. **Rationale:** Direct match to privacy and scope requirements. **Alternatives:** Server generation would transmit private text and add infrastructure. **Trade-off:** Browser memory/CPU and bundled assets need later measurement. **Evidence:** Phase 1 Playwright drives the browser implementation of pdfmake and PDF.js; no app network API is configured.

## TD-02 — Framework and dependency baseline

**Context:** Empty repository; source PDF p. 5 names React/TypeScript/Vite, Tailwind, pdfmake, PDF.js, Vitest, Playwright and Lucide. **Decision:** React 19, Vite 8, TypeScript 6 strict, Tailwind 4 plugin, pdfmake 0.3.15, pdfjs-dist 6, Lucide React, Vitest 5, Playwright 1.65 and ESLint 10; npm lockfile records exact resolutions. Manrope is self-hosted from its OFL-licensed Fontsource package. **Rationale:** Current compatible package line tested under Node 26.12/npm 11. **Alternatives:** Older compatible toolchain; unnecessary given current runtime. **Trade-off:** Vite 8 and PDF.js 6 require Node 22.13 or newer; current host was Node 26.12.1. **Evidence:** `npm run typecheck`, lint, unit tests, Playwright test and build recorded in `IMPLEMENTATION_LOG.md`; clean install audited 0 vulnerabilities.

## TD-03 — Domain boundaries

**Context:** Source PDF p. 7 calls for small typed modules and separates raw input, normalized content, paper, snapshot and generation errors. **Decision:** `src/types/domain.ts` contains React-independent data contracts; `features/pdf` owns layout configuration and generation; `features/preview` owns byte inspection. The shell imports the generation code only on action. **Rationale:** Keeps UI independent and makes the feasibility path executable without starting future processing/UI scope. **Alternatives:** A service/class layer or state manager; no current need. **Trade-off:** Phase 2/3 may refine field names as requirements become executable.

## TD-04 — A4 PDF geometry and header

**Context:** Source PDF p. 4 fixes A4 portrait, 15 mm margins, 6 mm gap, equal columns, 16/11/12 pt hierarchy and no spacing. **Decision:** `PDF_LAYOUT` centralizes those values; `millimetersToPoints` uses `mm × 72 / 25.4`. A pdfmake page `background` callback paints title and artist at 15 mm from the top; body top margin reserves 34 pt for this header plus a 12 pt gap. White is the PDF default. **Rationale:** The full-width page layer repeats independently of the snaking lyric columns. **Alternatives:** Include header text in the lyrics stream (would repeat only once); custom page drawing (more code). **Trade-off:** Single-line metadata that exceeds usable width is rejected safely; dynamic wrapping and its reservation are Phase 4. **Evidence:** PDF.js checks actual dimensions, extracted metadata/header coordinates, body/header separation and bounds; Playwright renders every page of a multi-page PDF to canvas and confirms visible header ink.

## TD-05 — Native continuous column flow

**Context:** Source PDF pp. 4–6 require left→right→next page reading order and explicitly ask to verify native behavior. **Decision:** Use pdfmake 0.3.15 `columns` with `snakingColumns: true`, lyrics in the first column and an empty second overflow target. The official pdfmake columns documentation identifies this as newspaper-style flow and documents its availability since 0.3.5. No manual text splitter is used. **Alternatives:** Premeasure and distribute lyric lines, or write a custom pagination adapter. **Rationale:** Native flow avoids duplicate line-wrap/pagination code and is verified by actual generated output. **Trade-off:** Keep pdfmake locked; Phase 3/4 must add section-boundary and long-line cases beyond this feasibility fixture. **Evidence:** PDF.js found every marker 001–240 once and in order across multiple columns/pages; column coordinates differ; every page contains both header values and body. Playwright pixel inspection confirms visible repeated headers on continuation pages.

## TD-06 — PDF.js byte ownership and worker

**Context:** PDF.js transfers data buffers to its worker, which can detach them. **Decision:** `getPdfPageCount` copies `Uint8Array` before passing it to PDF.js and destroys its loading task in `finally`. The worker URL is emitted by Vite from the matching installed `pdfjs-dist` package. PDF libraries load only when the feasibility action runs. **Rationale:** Preserve the original bytes for the future same-snapshot download; avoid loading multi-megabyte bundles before use. **Evidence:** Unit test reproduced buffer detachment when passing the original buffer; the copy fixed it. Playwright proves browser generation plus PDF.js page counting; production build includes the worker asset.

## TD-07 — Interface typeface and Aptos licensing

**Context:** Manrope is required for interface text (source PDF p. 8); Aptos is preferred for the PDF (p. 4). **Decision:** Use package-supplied Manrope Variable under SIL OFL 1.1 for the interface and carry its license at `public/licenses/Manrope-OFL.txt`. Do not bundle Aptos. No Aptos file is installed/available in this workspace. Microsoft says system font redistribution is generally not allowed; document embedding is a separate permission controlled by font embedding flags, while app/server redistribution needs extended rights. Aptos is supplied through Office; no asset-specific license or embedding flags were available to inspect. A public web app serving its own font file therefore has no verified redistribution permission in this project. PDFMake can consume TrueType/OpenType assets, but compatibility does not grant rights. Production generation uses pdfmake’s bundled Roboto VFS faces under OFL, with notice at `public/licenses/Roboto-OFL.txt`; Regular and Medium (the VFS bold mapping) are embedded. This is the licensed current core fallback, not a claim of Aptos equivalence. **Alternatives:** Obtain a suitable Aptos web/app license; retain the licensed embedded fallback. **Trade-off:** Roboto coverage is Latin/romanized and other glyphs are rejected until Phase 4 fallback. **Evidence:** official sources: [Microsoft Font redistribution FAQ](https://learn.microsoft.com/en-us/typography/fonts/font-faq), [Microsoft Aptos family](https://learn.microsoft.com/en-us/typography/font-list/aptos), [Manrope OFL](https://github.com/google/fonts/blob/main/ofl/manrope/OFL.txt), [Roboto OFL](https://github.com/google/fonts/blob/main/ofl/roboto/OFL.txt). **Unresolved:** Aptos can replace the fallback only after rights for a specific asset and PDF embedding are verified.

## TD-08 — Multilingual font feasibility

**Context:** Source PDF pp. 6–7 and 13 require future English, Filipino, Korean, Japanese, Chinese and mixed-script handling with no silent missing glyphs. **Decision:** Keep script-aware fonts/fallback for Phase 4. The current pdfmake bundled Roboto VFS is suitable only for Latin/romanized feasibility and does not preserve Hangul/CJK glyphs (PDF.js exposes NUL glyphs). A locally available Noto Sans JP Regular OpenType face was smoke-tested through pdfmake’s Node API: Japanese and tested Traditional Chinese characters extract; Hangul does not. The test is conditional on the licensed font being present at the OS font path and the font is not copied into app assets. **Alternatives:** Bundle Noto Sans JP/KR/SC/TC in phase 4 or license another unified/script-specific solution. **Trade-off:** Script-specific font files increase application and PDF sizes; the JP face is not a Korean fallback. Noto project font software is OFL; redistribution must carry the relevant copyright/license notice. **Evidence:** local smoke test plus [Noto CJK upstream license](https://github.com/notofonts/noto-cjk/blob/main/Sans/LICENSE) and [script coverage](https://github.com/notofonts/noto-cjk/blob/main/Sans/README-third_party.md). **Limit:** Limited text extraction smoke only; rendered multilingual glyph fidelity is not a Phase 1 claim.

## TD-09 — Lyrics processing and generation boundary

**Source requirements:** Normalize CRLF/CR and BOM, trim outer blanks, collapse repeated blank lines to one, preserve stanza breaks, recognize only complete supported bracketed labels, remove performer suffixes only from those labels, preserve unknown content/Unicode/repetitions, and remove only clearly identified site chrome (source PDF pp. 3, 6, 13). Validate title, artist, lyrics, and usable portrait paper geometry before generation.

**Implementation decisions:** `normalizeLyrics` retains the original `rawText`, emits normalized `text`, ordered `sections` and warnings. Labels are case-insensitively matched against Intro, Verse (optional number), Pre-Chorus, Chorus, Post-Chorus, Bridge, Refrain, Outro, Instrumental, Instrumental Break and Interlude; matched label spelling/case and numbering are retained while suffixes after a colon are removed. Unknown or inline bracketed text remains body text. Genius cleanup removes only a standalone HTTP(S) URL containing `genius.com`; ambiguous strings such as “Embed”, “Share”, “You might also like”, “Contributor”, “See you” and lyric-ending numbers remain untouched. `processSongInput` returns a discriminated success result with preserved metadata/raw lyrics, normalized content, resolved paper, geometry and warnings; failure returns issues without generation data.

**Paper decisions:** `PAPER_SIZES` is the single standard-preset registry in millimeters (A3/A4/A5/A6, ISO B4/B5, Letter, Long Bond and Legal); A4 is the default. Custom mm/in values resolve to millimeters without rounding. `paper-dimensions.ts` exposes the conversion functions; mm-to-points reuses the compatible implementation from `layout-config.ts`. Geometry converts dimensions, margins and gutter to points and checks positive equal-column width and body height after the existing 34 pt header reservation and 12 pt gap. Custom landscape sizes and unusable/non-finite dimensions are rejected. No arbitrary min/max limits were added because the source specifies none.

**Phase boundary:** Phase 2 provides pure parsing, validation, paper resolution and foundational geometry only. Phase 3 consumes `processSongInput` success data and resolved dimensions, measures supported glyphs/headers/tokens, renders the PDF, and verifies output. Script fallback, exhaustive pagination edge cases and dynamic header wrapping remain Phase 4.

## TD-10 — Production PDF generation boundary and safety

**Context:** Phase 3 must produce real, selectable PDFs for registered and custom portrait paper while preserving the normalized song and keeping lyrics in browser memory. **Decision:** `generatePdf(ValidatedSong)` owns production rendering and returns a `PdfSnapshot` containing a copied byte buffer, PDF Blob, page count, resolved paper, geometry, and sanitized filename. The renderer uses the Phase 2 dimensions converted to points and passes a custom point-size page to pdfmake; continuous two-column flow uses equal columns and native snaking. A repeated full-width monochrome header reserves the documented title/body gap. No synthetic balancing or font scaling is used. **Font:** Register pdfmake's OFL-licensed embedded Roboto Regular and Medium faces (Medium is the VFS bold face); use fontkit cmap and metrics checks before rendering. Unsupported glyphs, multiline/overwide headers, and unbreakable tokens wider than a column fail with generic typed errors and no lyric text in logs/errors. This core Latin/romanized coverage is not the Phase 4 mixed-script solution. **Page safety:** reject page dimensions above 14,400 pt, the default maximum user-space coordinate in Adobe's PDF reference, to avoid pathological dimensions. **Filename:** strip path/control/invalid filename characters, handle reserved device names, and bound the stem length. **Evidence:** actual generated PDF.js extraction and page-box checks cover every registered preset and custom dimensions; 240 ordered flow markers across pages; embedded font presence; representative rendered pages; safe failure tests. See [Adobe PDF Reference, User space](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf). **Trade-off:** Unsupported glyphs are rejected until Phase 4 provides suitable embedded script fonts; oversized indivisible tokens are safely rejected rather than scaled.

## TD-12 — Phase 5 workspace and generation lifecycle

**Context:** Source PDF pp. 8–10 specifies an editorial workspace with the editor before the document area on mobile and side-by-side on desktop. Phase 5 connects validated song input to the actual Phase 3 generator while reserving real PDF rendering and download for Phase 6. **Decision:** `src/App.tsx` owns a small controlled in-memory form and lifecycle state; no state library, persistence, network submission, or preview byte copy is introduced. `processSongInput` remains the validation/normalization boundary. The generator is dynamically imported only after successful validation and returns the `PdfSnapshot` kept in component state. Edits are compared with a canonical identity over title, artist, raw lyrics, and paper; switching display units does not mark unchanged physical dimensions stale. Custom dimensions retain raw strings (including blank/invalid values) alongside canonical mm values so unit switching does not discard invalid input or accumulate conversion drift. Document facts come from the generated snapshot and dimensions are rounded only for display.

**Lifecycle/accessibility:** Keep document space stable for empty, loading, generated, stale, and error states. A generated snapshot is labeled previous when the current form changes; regeneration uses current raw input. Reset asks for confirmation only when user data/settings/snapshot would be discarded, invalidates outstanding work, and focuses the title field. Validation uses domain issues, associates inline text with fields, announces summary/status, and focuses the first invalid control. Native labels/controls, visible keyboard focus, contrast, and reduced-motion behavior are retained.

**Phase boundary:** The Phase 5 document area reports the true snapshot filename, page count, paper, orientation, and byte size, but does not draw PDF pages. Navigation/zoom/fullscreen controls and Download are disabled. Phase 6 must connect PDF.js to the same retained snapshot bytes, handle worker/resource disposal and revision guards, and provide a download of exactly the previewed snapshot.

**Evidence:** Playwright covers required and custom inputs, conversion, real PDF snapshot metadata, errors/retry, stale/regenerate/reset, in-flight reset, lazy module loading, keyboard/accessible names, primary text and control-boundary contrast, reduced motion, and no horizontal overflow at 320/375/768/1024/1280/1440 px. Browser screenshots were visually inspected for these widths and empty, loading, validation, generated, stale, and error states. Full Phase 5 check results are in `docs/IMPLEMENTATION_LOG.md`.

## TD-11 — Phase 4 multilingual layout and pagination

**Context:** Phase 4 requires selectable mixed Latin/Korean/Japanese/Simplified Chinese/Traditional Chinese output, reliably wrapped headers, Unicode-safe lyric wrapping, and deterministic section-aware two-column flow. **Font decision:** retain pdfmake VFS Roboto for verified Latin/Filipino coverage. Bundle official static Noto Sans CJK SubsetOTF version 2.004 JP, KR, SC and TC regular and bold faces from release `Sans2.004`, licensed OFL 1.1; checksums, byte sizes, license copy and upstream provenance are in `docs/THIRD_PARTY_NOTICES.md`. Load fixed same-origin assets on demand, deduplicate concurrent loads, cache parsed fontkit faces and retry after failed loads. Actual cmap checks select a preferred script face; fallback tries other loaded faces by coverage. Unsupported graphemes return generic `unsupported-glyph` errors. Han-only ambiguous text defaults deterministically to Japanese; Kana/Hangul context and Simplified/Traditional region clues select other regional faces. This is not a universal Unicode or language-identification claim.

**Layout decision:** Use `Intl.Segmenter` grapheme boundaries and UAX 14 line-break opportunities (`linebreak`) with fontkit metrics. Dynamic title and artist lines wrap at full usable page width; their measured block determines the repeated header and exact body top. Keep a section label with its first visual lyric line. A pure paginator places units down the left column, then the right column, then the next page; it suppresses boundary separators and terminal blank pages while preserving source text and order. Exact-fit and too-tall-item outcomes are explicit.

**Renderer adapter:** Retain pdfmake for PDF generation and font embedding. Feed planned pagination through explicitly positioned text nodes with page-break-before markers instead of native `snakingColumns`: a fixture planned for 3 pages produced 5 pages with native stacks because pdfmake's internal wrapping/column flow did not match measured line placement. The adapter's generated PDF.js page count matches the pure plan in tested column and page boundary fixtures. This follows the authorized fallback for renderer disagreement. It does not balance columns or scale text.

**Evidence / limits:** `npm run test` covers mixed runs, actual fonts, extraction, repeated dynamic headers, custom paper, wrapping, boundaries, exact fit, section grouping and typed failure. Chromium verifies same-origin lazy requests, no CJK requests for Latin-only input, mixed-script extraction, continuation headers, stable PDF bytes and rendered canvas content. PDF.js extraction composes a decomposed accent to its NFC-equivalent character during font shaping/extraction; user input is not normalized or mutated before layout and the semantic text is equivalent, but code-point-identical NFD extraction is not promised. Aptos remains preferred by the source spec but unavailable with verified redistribution rights, so it is not bundled.

## TD-13 — Phase 6 PDF.js preview and same-snapshot download

**Context:** The Phase 5 editor retains one immutable `PdfSnapshot`; source PDF pp. 9–11 require preview of the generated document and download of that same document, responsive controls, stale handling and safe resource cleanup. **Decision:** `src/features/preview/pdfjs-runtime.ts` imports the installed PDF.js legacy runtime and its matching Vite-emitted worker only after a snapshot exists; the text-layer stylesheet is lazy-loaded alongside it. `PdfPreview` passes a defensive `snapshot.bytes` copy to PDF.js, checks loaded page count against snapshot metadata, renders one selected page at a time to a high-DPI canvas and PDF.js `TextLayer`, and retains the same snapshot Blob for download. The viewer uses 96 CSS px / 72 PDF pt, default fit-page, fit-width, manual 50–200% zoom in 25% stops, page navigation, native fullscreen with an inert-background/keyboard-trapped CSS fallback, and canvas safety limits of 16 million pixels / 8192 px per side. Download is eligible only when the current snapshot page and text/canvas rendering are ready, generation is idle, and the source identity is current. A hidden temporary anchor downloads the snapshot Blob using its sanitized filename; its object URL is revoked after the browser has started the download.

**Lifecycle and races:** A serialized disposal queue cancels render/text-layer work, cleans the active page, destroys PDF.js loading tasks/documents on snapshot replacement/reset/unmount, clears the canvas backing store and text layer, and keeps newer loads ordered behind prior cleanup. Render/document revisions and snapshot identity gate async state publication. The generation request is locked synchronously to prevent overlapping generator runs; invalidated results cannot replace the current snapshot. Starting a same-input replacement marks the retained snapshot as needing refresh so a failed replacement cannot make that old snapshot downloadable as current. Display-unit changes preserve a valid canonical custom-paper identity.

**Evidence:** PDF.js 6.5.438 API/runtime and matching legacy worker were verified from the installed package. Unit tests cover zoom/fit/canvas caps, byte ownership and Blob integrity, and filename-based download dispatch. Chromium tests prove actual non-white canvas pixels, extracted/selectable page text, multipage navigation, zoom/fit transitions, stale download blocking, CSS fullscreen focus/escape behavior, lazy runtime loading, responsive no-overflow at 320 px, and browser download bytes equal to the array buffer transferred into PDF.js. The production worker and CSS chunks are emitted by Vite. Full phase checks and production-browser result are in the 2026-11-26 Phase 6 implementation log entry.

**Trade-offs and limits:** Only the active page is rasterized, keeping canvas memory bounded; switching pages rerenders that page. Extreme zoom/large paper may require internal panning and the canvas scale is reduced to stay within the explicit memory limits. Native fullscreen depends on browser support; the accessible CSS fallback is available otherwise. The browser object URL has a one-second cleanup delay to allow download handoff. This phase does not claim a manual screen-reader certification or Phase 7 deployment/release review.

## TD-15 — Renderer-aligned pagination height

**Context:** The exact local Legal reproduction passed input processing and PDF byte generation, but page inspection raised `inspection-failed`: the paginator planned one page and pdfmake emitted two. The same input with spacing substitutions retained the failure, while an anonymized fixture preserving the relevant font-width and glyph-height profile reproduced it without lyric text. pdfmake computes each rendered text line from the font ascender/descender metrics; the paginator had reserved only the measured glyph box (minimum 12 pt). For Roboto at 12 pt, pdfmake's renderer line box is 14.0625 pt.

**Decision:** Preserve `heightPt` for the existing visual line placement, and calculate a separate `paginationHeightPt` as the maximum of that visual box, glyph extent, and the font-metric line box. Use the larger bound for line and keep-with-first-line pagination. Keep PDF.js planned-versus-actual page-count inspection strict; do not shrink, omit, or truncate text.

**Evidence / limits:** A fixed anonymized near-boundary Legal fixture fails before the change with planned 1 / actual 2 and passes after it. The exact local input now generates a two-page Legal PDF whose PDF.js count agrees with the snapshot, retains extracted lyrics, and whose Blob equals the snapshot bytes. Browser preview/download verification after this change is still blocked by local loopback network restrictions; Brave has not been tested. Phase 7 remains in progress.

## TD-16 — Separate renderer fit from visual column advancement

**Context:** Follow-up review showed that adding `paginationHeightPt` to the column cursor for each line accumulates renderer-only leading even though absolute PDF line positions advance by `heightPt`. That is safe but can move a following line that would fit at its actual visual position and can create avoidable pages. The engine-level exact-input output had two pages under this cumulative reservation.

**Decision:** Keep `PaginatedColumn.usedHeightPt` as the visual placement cursor and accumulate `heightPt`. For each proposed line or atomic section-start group, calculate each renderer extent at its visual start position and require the maximum end to remain within the usable column height. Keep all heading lines and the first rendered lyric line atomic, check their extents sequentially, and preserve the strict PDF.js planned-versus-actual page-count guard. Do not reduce the renderer safety bound or change any approved geometry, typography, or spacing.

**Evidence / limits:** Unit tests fail under cumulative-reservation semantics and pass with the visual-cursor/renderer-fit model. The exact local input now yields one Legal page (612 × 1008 pt) rather than two; PDF.js confirms page count, extracted canonical section labels, and equal Blob/snapshot bytes. A Poppler raster inspection confirmed the two columns, retained title/artist, and a fully occupied first column without clipping. Local browser access remains blocked; engine verification does not establish preview/download behavior. See the Phase 7 log and release checklist for current evidence.

## TD-17 — Conservative canonical section-label parsing

## TD-18 — Centralized 48-type section registry

**Context:** The latest release regression showed that Rap and many other recognized musical sections were not represented by the previous fixed label expression. Missing recognition also bypasses the existing structured-section pagination path.

**Decision:** Keep one readonly `SECTION_REGISTRY` in `src/features/lyrics/section-labels.ts`. Each entry contains a canonical name and explicit aliases; the registry states that optional decimal numbering is preserved for all registered types. Matching is case-insensitive, collapses heading whitespace, and checks longer tokens before shorter overlapping names. The parser requires a complete standalone bracketed candidate and reconstructs output from the canonical name and optional digits. It returns separate annotation-kind metadata for parenthesized song references, performer suffixes, and Medley song lists while retaining the existing `label` and `hasPerformerSuffix` fields.

**Annotation and preservation rules:** All registered names share the same balanced-parenthesis and nonempty-colon grammar. Only a fully valid heading is normalized. A bounded single continuation is permitted when an annotation is visibly incomplete, including performer lists split after a comma; unknown names, malformed syntax, ambiguous continuations, inline brackets, and ordinary lyric text remain untouched. No artist lookup or external classification is used.

**Integration and evidence:** Normalized headings enter the existing `LyricsSection` path, so `generate-pdf.ts` and the section-aware paginator require no semantic-name special cases. Independent expected-name tests assert all 48 registry entries, aliases, numbering, annotations, negative cases, and preservation. Actual Long Bond PDF tests extract all 48 canonical labels, full synthetic lyric text, paper dimensions, metadata, page count, and same-byte snapshot integrity. The pagination engine and completed visual-fit/renderer-reservation behavior were not changed.
